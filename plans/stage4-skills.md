# 段階 4: スキル機構

- 状態: 完了（2026-11-03、記録: docs/stage4-skills.md）
- 見積もり: 1〜1.5 日（仕組みとスキル 3 つ 半日、WSL での確認 2 時間、Pi での確認と遅延の測定 半日）

## 目的

LLM のツール呼び出し（Messages API の tools）で、答えるだけでなく「調べる・記録する」ができるようにする。
スキルは 1 ファイル 1 つで足せる形にし、あとから増やしやすくする。

## 完了条件

| 条件 | 確かめ方 |
|---|---|
| スキルが 3 つ以上あり、Claude が質問に応じて選んで呼ぶ | `scripts/skill_check.py`（WSL・Pi どちらでも動く。STT/TTS を通さず文字で聞く）で、決めた質問 10 問ほどについて「呼ばれたスキル」が期待どおりか合否を出す。全問合格 |
| そのうち 1 つは LIFE（mat-dev-io/LIFE）への記録 | Pi で「R2D2、LIFE に〜と記録して」と声で頼み、LIFE に記録ができる（決めてほしいこと 1 の形で）。読み上げで何を記録したか返す |
| スキルを使わない質問の遅延が段階 3 から悪化しない | `logs/latency.jsonl` の合計の中央値を段階 3（約 3.1 秒）と比べる。悪化は 0.3 秒以内 |
| スキルを使う質問の遅延を記録する | 同じログに呼んだスキル名と、スキルの実行時間・LLM の往復回数を足し、中央値を出す（目標値は置かず測るだけ） |
| スキルが失敗しても一周が止まらない | ネットワークを切る・トークンを外すなどで失敗させ、「記録できませんでした」のように声で返ることを確かめる |
| 音の入出力に触らない | 触らないので `loopback.sh` は不要。もし触ったら流す |
| 結果を `docs/stage4-skills.md` に書き、CLAUDE.md・`.env.example` を直す | 記録ファイルがある |

## やらないこと

- 会話の履歴（1 問 1 答のまま。「さっきのを取り消して」はできない）
- タイマー・アラームのような、あとから鳴らすスキル（呼びかけの待ち受けと並行して動かす仕組みが要るので段階を分ける）
- 声での確認のやりとり（「記録してよいですか」「はい」）。代わりに、記録した内容を読み上げで返す
- MCP サーバーや Agent SDK への載せ替え（自前の小さなループで足りる）
- LIFE 側のリポジトリの変更（ラベルの追加なども、要るなら別に頼む）
- 音の入出力・ウェイクワードの変更

## 手順

1. **仕組みを作る**: `assistant/skills/` に 1 スキル 1 ファイルで置く。各ファイルは名前・説明・入力の JSON Schema・実行する関数を持つ。`assistant/llm.py` の `ask()` を、ツールの呼び出しがあれば実行して結果を返し、答えが出るまで回す形にする（往復は最大 3 回）。スキルの例外は捕まえて `is_error` の結果として Claude に返す。`.env` の `SKILLS` で使うスキルを選べるようにする（空なら段階 3 と同じ動き）
2. **スキルを 3 つ作る**（中身は決めてほしいこと 2）
   - LIFE への記録は `LIFE_DRY_RUN=1` で実際には書かず、書く予定の内容をログに出すだけにできるようにする
3. **WSL で確かめる**: `scripts/skill_check.py` を足す。質問の文字列と期待するスキル名の組を持ち、Claude にスキル付きで聞いて、呼ばれたスキル・答え・時間を表で出し、合否を終了コードで返す（`loopback.sh` と同じく 0 / 1 / 2）。LIFE は dry-run で流し、最後に 1 回だけ本当に書いて、LIFE 側で見えることを確かめる
   - ここで止めて、合否の表と LIFE にできた記録を見せる
4. **Pi に載せる**: `deploy.sh` で配置し、`.env` に LIFE 用のトークンを入れる（決めてほしいこと 3）。Pi で `skill_check.py` を流してから、声でスキルごとに数回ずつ頼む
5. **遅延を測る**: `logs/latency.jsonl` にスキル名・スキルの時間・往復回数を足し、スキルあり・なしで中央値を出す（`scripts/latency_summary.py` を必要なら直す）
6. **記録を書く**: `docs/stage4-skills.md` に結果を書き、この計画を「完了」にする

## 決めてほしいこと

決まったこと（2026-11-03）:

1. **LIFE に何を記録するか**: Issue を作る。タイトルに言ったこと、本文に「音声アシスタントから記録（日時）」を入れる。ラベルは付けない（本文の一行で見分ける。LIFE 側は変えない）
2. **残りのスキル**: 今の日時（ネットワーク不要）と天気（Open-Meteo。API キー不要。地点は `.env` の緯度経度で固定）
3. **Pi に置く GitHub のトークン**: fine-grained PAT を LIFE だけ・Issues の書き込みだけ・期限 90 日で人が作り、Pi の `.env` の `LIFE_GITHUB_TOKEN` に入れる。gh CLI は Pi に入れず、httpx で REST API を直接呼ぶ

## リスク

- **遅延が延びる**: スキルを使うと Claude との往復が 1 回増え、1〜2 秒ほど延びそう。使わない質問でもツールの定義の分だけ入力が増える。代わりの手: スキルを使う回だけ「調べます」と先に一言読み上げる（手順 5 の結果を見て、要れば別の構成変更で）
- **Claude がスキルを選び間違える**: 「記録して」以外でも記録したり、逆に呼ばなかったりする。`skill_check.py` に紛らわしい質問（「LIFE って何？」など記録しないもの）を入れて確かめ、説明文で直す
- **誤認識のまま記録される**: STT の誤りがそのまま LIFE に残る。確認のやりとりはしない代わりに、記録した文を読み上げて返し、変なら人が LIFE で直す
- **トークンが Pi にある**: Pi が乗っ取られると LIFE に書かれる。権限を Issues だけ・LIFE だけに絞り、期限を付ける。`.env` はコミットしない（既に .gitignore 済み）
- **server-side fallback とツールの併用**: いまの `ask()` は安全分類器の fallback の beta を使っている。ツールと一緒に使えない・挙動が変わる場合は、スキル付きの呼び出しでだけ外す（手順 1 で確かめる）
