# 構成変更 C3: 性能の自動ベンチマークと劣化での停止

- 状態: 完了（2026-11-03、記録: docs/c3-perf-gate.md）
- 見積もり: 30 分（実装 10 分、基準の測定 8 分、わざと劣化させる確認 5 分、記録 7 分）＋直し 15〜20 分

## 目的

性能に関わる変更をしたら、頼まれなくても遅延と精度のベンチマークが走り、基準より悪くなっていたらコミットの前で止まって人に知らせる。
段階 4 で「p90 が延びたが気づくのが記録を書くときだった」ことをなくす。

## 完了条件

| 条件 | 確かめ方 |
|---|---|
| 性能に関わる変更のあと、頼まなくてもベンチが走る | `assistant/`・`requirements.txt`・`systemd/` を変えて `git commit` しようとすると、Claude Code のフックが `scripts/perf_gate.py` を走らせる（前回合格したときから対象のファイルが変わっていなければ走らない） |
| 劣化していたら止まって人に知らせる | `perf_gate.py` が終了コード 1 を返すと、フックがコミットを止め（exit 2）、どの指標がどれだけ悪いかを Claude に返す。CLAUDE.md に「止まったら直さずに人に報告する」と書く |
| 何を劣化とみなすかと、その決め方が文書にある | `docs/c3-perf-gate.md` に指標・しきい値・基準の測り方（同じコードで 3 回流したばらつき）を書く |
| わざと劣化させた変更で 1 回止まる | `assistant/llm.py` に `time.sleep(0.5)` を足してコミットしようとし、止まることを確かめてから戻す。結果を記録に書く |
| CLAUDE.md にいつ使うかを書く | CLAUDE.md の差分 |

## やらないこと

- ウェイクワードの見逃し・誤検知（`ww_measure.py`。実際に音を流すので時間がかかる）と音の入出力（C1 の `loopback.sh`）はゲートに入れない
- GitHub Actions など CI で回すこと（Pi と録音が手元にしかない）
- 人が手でコミットするときの git の pre-commit フック（今回は Claude Code の作業だけを止める。決めてほしいこと 1）
- 劣化の原因を自動で切り分けること

## 手順

1. **ベンチの本体**: `scripts/perf_bench.py`（Pi で動く）。アシスタントを止めた状態で次を流し、結果を 1 つの JSON で出す
   - 遅延: 段階 1 の録音 9 問を `main.py --wav` と同じ `Pipeline` に 2 周通す（18 回）。音は再生しない（`--no-play` を足す。`total_ms` は再生開始までなので値は変わらない。`stall_ms` は使わない）
   - STT の精度: 同じ 9 問の CER（`stt_bench.py` の計算を使う）
   - スキルの選び方: `skill_check.py` の 10 問の合格数
2. **ゲート**: `scripts/perf_gate.py`（WSL。標準ライブラリだけの Python。比べる処理が要るので sh ではなくした）。`deploy.sh` → Pi で `perf_bench.py` → 基準 `bench/baseline.json`（コミットする。IP やキーは入れない）と比べて、指標ごとの表と合否を出す。終了コード 0 / 1 / 2（`loopback.sh` と同じ）。合格したら対象ファイルのハッシュを `cache/perf_gate/passed` に残す。`--update-baseline` で基準を作り直す
3. **基準としきい値を決める**: 今の main で `perf_bench.py` を 3 回流し、回ごとの中央値のばらつきを見て、しきい値を決める（決めてほしいこと 2）。`bench/baseline.json` に値としきい値を書く
   - ここで止めて、3 回の値と決めたしきい値を見せる
4. **自動で走らせる**: `.claude/settings.json` に PreToolUse フック（Bash の `git commit`）を足す。対象ファイルが前回合格から変わっていれば `perf_gate.py` を走らせ、1 か 2 ならコミットを止める
5. **わざと劣化させて確かめる**: `llm.py` に `sleep(0.5)` を足してコミットを試み、止まることと表示を確かめる。戻してもう一度試み、通ることを確かめる
6. **記録**: `docs/c3-perf-gate.md`、CLAUDE.md に一行、この計画を「完了」にする

## 決めてほしいこと

決まったこと（2026-11-03）: 1 は A（コミットの直前）、2 は案のとおり（p90 は表示だけ）。

直したこと（2026-11-03、再承認済み）: 最初の案では、`llm.py` に足した 0.5 秒の待ちを見逃した。合計の中央値は基準より +121 ms しか延びず、合格になった。Claude API の待ち時間が時間帯で数百 ms 揺れて、0.5 秒が埋もれたため。そこで判定を次のように変える（2 の案を置き換える）
- `llm.py` で、API の呼び出しにかかった時間（`api_ms`）と入力トークン数（`input_tokens`）を記録する（`logs/latency.jsonl` にも残す）
- 判定に使う: 手元の処理時間（`total_ms − api_ms`）の中央値が基準 + max(100 ms, 3 回のばらつき) を超えたら劣化 / 入力トークン数の中央値が基準の +20% を超えたら劣化 / STT の中央値 +20% / CER +2 ポイント / スキル 10/10
- 表に出すだけ: 合計の中央値と p90、API の待ち時間（自分では直せない揺れが大きい）。モデルや effort が基準と違えば注意を出す

1. **いつ走らせるか**
   - A（おすすめ）: Claude Code のフックで、`git commit` の直前に走らせる。対象ファイルが前回合格から変わっていなければ飛ばす。1 回 2〜3 分かかるので、編集のたびではなくコミットの単位にする
   - B: 編集のたび（PostToolUse）に走らせる。確実だが、1 つの変更で何度も 2〜3 分待つ
   - C: A に加えて git の pre-commit フックも入れ、人の手のコミットも止める
2. **劣化とみなす指標としきい値**（案。手順 3 の 3 回の値を見て最終決定し、記録に理由を書く）
   - 合計 `total_ms` の中央値: 基準 + max(300 ms, 3 回のばらつき（最大 − 最小）) を超えたら劣化。300 ms は段階 4 の完了条件で使った許容幅
   - STT `stt_ms` の中央値: 基準の +20% 超（ローカルで動くので Claude よりばらつきが小さい）
   - STT の CER: 基準 + 2 ポイント超（9 問・約 100 文字なので 2 文字分）
   - スキルの選び方: 10/10 でなければ劣化（今の CLAUDE.md の基準と同じ）
   - p90 と Claude・TTS の区間は表に出すだけで判定には使わない（段階 4 で p90 は同じ設定でも 3.3〜4.1 秒と揺れたため、止めすぎる）

## リスク

- **Claude の遅延のばらつきで、劣化していないのに止まる**: しきい値をばらつきから決め、さらに 1 回だけ流し直して 2 回とも悪いときだけ不合格にする（C1 の流し直しと同じ考え）
- **フックの待ち時間**: 2〜3 分コミットが止まる。フックのタイムアウトを 15 分にする。Pi に届かないときは 2（環境エラー）で止め、黙って通さない
- **フックが `git commit` を見逃す**（`git -C` や別名など）: 文字列の一致で拾える範囲に限る。CLAUDE.md にも「コミット前に流す」と書いておき、二重にする
- **API の料金**: 1 回で Claude を約 28 回呼ぶ（effort low）。走るのは対象ファイルを変えたコミットだけ
