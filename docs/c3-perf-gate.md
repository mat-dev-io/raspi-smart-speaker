# 構成変更 C3: 性能の自動ベンチマークと劣化での停止

性能に関わるファイルを変えてコミットしようとすると、頼まなくても遅延と精度のベンチが Pi で走る。基準より悪ければコミットを止めて人に知らせる。

2026-11-03 実施。Pi 5（段階 4 と同じ構成）。計画は [plans/c3-perf-gate.md](../plans/c3-perf-gate.md)。

## 結果

| 完了条件 | 結果 |
|---|---|
| 性能に関わる変更のあと、頼まなくてもベンチが走る | OK: `git commit` の直前に Claude Code のフックが `scripts/perf_gate.py --check-only` を走らせる。`assistant/`・`requirements.txt`・`systemd/` が前回合格から変わっていれば、配置してベンチを流す（1 回約 1 分 40 秒） |
| 劣化していたら止まって人に知らせる | OK: 不合格ならフックが exit 2 でコミットを止め、指標の表を Claude に返す。CLAUDE.md に「直そうとせず人に見せる」と書いた |
| 何を劣化とみなすかと、その決め方が文書にある | この文書の「判定」 |
| わざと劣化させた変更で 1 回止まる | OK: `ask()` の先頭に 0.5 秒の待ちを足してコミットすると、手元の処理時間が 656 → 1144 / 1141 ms（2 回とも NG）で止まった。ただし最初の判定（合計で見る）では見逃したので、指標を直した（下記） |
| CLAUDE.md にいつ使うかを書く | OK（「性能」の行） |

## 使い方

```bash
python3 scripts/perf_gate.py                       # 配置 → ベンチ → 判定（WSL）。0 = 合格 / 1 = 劣化 / 2 = 環境エラー
python3 scripts/perf_gate.py --check-only          # 対象のファイルが前回合格から変わっていなければ流さない（フックが使う）
python3 scripts/perf_gate.py --update-baseline 3   # 意図して設定を変えたときだけ。3 回流して bench/baseline.json を作り直す
```

- フック: `.claude/settings.json` の PreToolUse（Bash）→ `.claude/hooks/perf_gate_hook.sh`。コマンドに `git commit`（`git -C DIR commit` も）があるときだけ動く。タイムアウトは 15 分
- フックの設定は Claude Code の起動時に読まれる。足したり変えたりしたら `/hooks` を開いて読み込ませる（今回、読み込む前のコミットは素通りした）
- ベンチの本体は `scripts/perf_bench.py`（Pi）。アシスタントを止めて流し、終わったら起動し直す。音は再生しない
- 全文のログは `cache/perf_gate/last.log`、合格の印は `cache/perf_gate/passed`（どちらもコミットしない）

## 判定

ベンチ 1 回で、段階 1 の録音 9 問を 2 周流し（1 件目は暖機なので除いて 17 件）、`skill_check.py` の 10 問を流す。

| 指標 | 劣化とみなす | 理由 |
|---|---|---|
| 手元の処理時間（合計 − API の待ち）の中央値 | 基準 + max(100 ms, 3 回のばらつき) を超えた | STT・TTS・自分のコードの時間。ネットワークを通らないので揺れが小さい（3 回で 630〜657 ms、ばらつき 27 ms）。100 ms は、ばらつきの約 4 倍で、見たい劣化（0.5 秒ほど）よりは十分小さい |
| 入力トークン数の中央値 | 基準の +20% を超えた | プロンプトやツールの定義が膨らむと API が遅くなる（段階 4 の p90）。時間と違って同じ質問ならほぼ同じ値になる |
| STT の時間の中央値 | 基準の +20% を超えた | ローカルで動くので揺れが小さい（3 回で 8 ms） |
| STT の CER | 基準 + 2 ポイントを超えた | 9 問で約 100 文字なので 2 文字分。同じ音・同じモデルなら毎回同じ値 |
| スキルの合格数 | 10/10 未満 | 段階 4 からの決まり |

- 表に出すだけで判定に使わないもの: 合計の中央値と p90、API の待ち時間、TTS の時間。モデル・effort・STT・声・スキルの設定が基準と違えば「注意」を出す
- 悪い指標があれば 1 回だけ流し直し、2 回とも悪かった指標だけを劣化とする

### 決め方（最初の案を直した経緯）

最初は「合計の中央値が基準 + max(300 ms, ばらつき)」で判定した。300 ms は段階 4 の完了条件で使った許容幅。同じコードで 3 回流した値は 2709 / 2792 / 2914 ms（ばらつき 205 ms）で、しきい値は 3092 ms になった。

しかし `llm.py` の `ask()` の先頭に `time.sleep(0.5)` を足しても、合計の中央値は 2913 ms（基準より +121 ms）で合格になった。Claude の区間（2161 → 2413 ms）も +250 ms しか延びていない。API の待ち時間が時間帯によって数百 ms 揺れ、足した 0.5 秒がその揺れに埋もれた。合計で判定する限り、しきい値を下げると劣化していなくても止まり、上げると見逃す。

そこで `llm.py` で API の呼び出しそのものの時間（`api_ms`）と入力トークン数を記録するようにし、自分では直せない API の待ちを判定から外した。`api_ms` と `input_tokens` は `logs/latency.jsonl` にも残る。

直したあとの基準（同じコードで 3 回、各 17 件。`bench/baseline.json`、2026-11-03）:

| 指標 | 1 回目 | 2 回目 | 3 回目 | 基準（中央値） | しきい値 |
|---|---:|---:|---:|---:|---:|
| 手元の処理の中央値（ms） | 657 | 630 | 656 | 656 | ≤ 756 |
| 入力トークン数の中央値 | 1044 | 1044 | 1044 | 1044 | ≤ 1253 |
| STT の中央値（ms） | 223 | 211 | 215 | 215 | ≤ 258 |
| STT の CER | 4.9% | 4.9% | 4.9% | 4.9% | ≤ 6.9% |
| スキルの合格数 | 10 | 10 | 10 | 10 | 10 |
| 合計の中央値（ms、表示のみ） | 2881 | 2719 | 2872 | 2872 | - |
| API の待ちの中央値（ms、表示のみ） | 2079 | 2057 | 1930 | 2057 | - |

合計のばらつきは 162 ms なのに対して、手元の処理時間は 27 ms で、入力トークン数は 0（毎回同じ）だった。

## わざと劣化させた確認

`assistant/llm.py` の `ask()` の先頭に `time.sleep(0.5)` を足し、ステージして `git commit` した。フックがゲートを流し、2 回とも NG になってコミットが止まった（約 3.5 分）。足した待ちを消すと、ファイルのハッシュが合格の印と同じに戻り、ベンチは流れずに通った。

| 指標 | 基準 | しきい値 | 1 回目 | 2 回目 |
|---|---:|---:|---:|---:|
| 手元の処理の中央値（ms） | 656 | ≤ 756 | 1144 ✗ | 1141 ✗ |
| 入力トークン数の中央値 | 1044 | ≤ 1253 | 1044 | 1044 |
| STT の中央値（ms） | 215 | ≤ 258 | 221 | 239 |
| 合計の中央値（ms、表示のみ） | 2872 | - | 3425 | 3099 |

確かめる途中でつまずいたこと:

- フックを足した直後のコミットは素通りした。Claude Code は起動時にフックを読むので、`/hooks` を開いて読み込ませる必要があった
- 「ファイルを書き換える && git commit」を 1 つの Bash コマンドにすると、フックは書き換える前のファイルを見るので、変わっていないと判断して通す（PreToolUse はコマンド全体が動く前に走る）。編集とコミットは別のコマンドにする（Edit ツールで直してからコミットするふつうの流れなら問題ない）

## 見逃すもの

- API の呼び出しそのものが遅くなる変更（モデルや effort の変更は「注意」で、プロンプトの肥大は入力トークン数で捕まえる。それ以外の、例えば出力が長くなる変更は捕まえない）
- ウェイクワードの見逃し・誤検知、音の入出力（それぞれ `ww_measure.py` と `loopback.sh`）
- 人が手でするコミット（git の pre-commit フックは入れていない）
- 編集とコミットを 1 つの Bash コマンドにまとめたとき（上記）
- フックの一致から漏れる書き方のコミット（別名など）。CLAUDE.md にも書いて二重にしている
